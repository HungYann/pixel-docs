## ADR-001：向量库选 pgvector 而非 Milvus

**状态**：已采纳  
**日期**：2026-05-25

### 背景

需要对商品做语义相似检索，支持以图搜图和 RAG 知识库召回。

### 方案对比

| 方案 | 适用规模 | P99（100万向量） | 运维复杂度 | 额外基础设施 |
|------|---------|-----------------|---------|------------|
| **pgvector** | < 1000 万 | **< 50ms（HNSW）** | 低（复用 PostgreSQL） | 无 |
| Milvus | 亿级 | < 50ms | 中（独立集群） | 需要 |
| Weaviate | 千万级 | ~80ms | 中 | 需要 |

### 决策

采用 pgvector（PostgreSQL 16 扩展），与业务数据库共用 PG 集群。

**理由**：
1. 商品向量规模预估 < 500 万，pgvector + HNSW 索引性能完全满足（P99 < 50ms）
2. 团队已有 PostgreSQL 运维经验，无需学习和维护独立向量数据库
3. 省去 Milvus 独立集群成本（机器 + 运维）
4. pgvectorscale 扩展预留了未来亿级扩展的能力

## ADR-002：LLM 分层选型策略

**状态**：已采纳  
**日期**：2026-05-25

### 背景

Agent Orchestrator 需要接入大语言模型做意图理解、内容规划和内容生成，不同任务对模型能力和成本的需求差异显著。

### 方案对比

| 方案 | 成本 | 延迟（国内） | 适用场景 | 数据合规 |
|------|------|-----------|---------|---------|
| **Claude 3.5 Sonnet** | 高 | 500-1000ms | 复杂推理、多步规划 | API 调用，注意数据出境 |
| **Gemini 1.5 Pro** | 中 | 500-1500ms | 多模态（图文/视频） | API 调用，注意数据出境 |
| **DeepSeek-Chat** | 低（¥0.014/K token） | 100-500ms | 高频低复杂度任务 | 国内部署 |
| 通义千问 | 低 | 100-300ms | 故障切换备用 | 国内部署 |

### 决策

**分层策略**：

```
复杂推理/多步规划  → Claude 3.5 Sonnet（质量优先）
多模态理解        → Gemini 1.5 Pro（能力优先）
意图解析/文案生成  → DeepSeek-Chat（成本优先）
故障切换备用      → 通义千问（兼容 OpenAI SDK）
```

**理由**：
1. 不同任务对模型能力要求不同，一刀切选最贵或最便宜都不合适
2. Claude 和 Gemini 用于高价值场景，单次调用成本可接受
3. DeepSeek 处理高频任务（意图解析每次对话都触发），成本降低约 10x
4. 所有模型兼容 OpenAI SDK，切换成本为零

## ADR-003：内容去重采用参数哈希缓存

**状态**：已采纳  
**日期**：2026-05-25

### 背景

相同商品、相同风格的视频生成请求会重复消耗 GPU 资源。

### 方案对比

| 方案 | 命中率 | 实现复杂度 |
|------|--------|---------|
| 不缓存 | 0% | 简单 |
| 完全相同参数缓存 | ~30% | 简单 |
| 语义相似缓存 | ~50% | 复杂（需向量检索） |

### 决策

采用参数 SHA256 哈希缓存，TTL 7 天。

**理由**：实现简单，30% 命中率已能显著降低成本（预计节省约 ¥50,000/月）；语义相似缓存收益增量不大但复杂度大幅增加，可后续按需添加。

## ADR-004：服务间通信选 REST/Webhook 而非 gRPC

**状态**：已采纳  
**日期**：2026-05-25

### 背景

系统内部服务间需要相互调用，需要选择统一的通信协议。

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| gRPC + Protobuf | 高性能、强类型 | 调试复杂、需维护 proto 文件、跨语言生态负担重 |
| **REST / HTTP** | 简单、易调试、生态成熟 | 相比 gRPC 性能略低（可接受） |
| Webhook | 异步解耦、低耦合 | 需要处理重试和幂等 |

### 决策

内部同步调用统一使用 REST API，异步回调使用 Webhook，消息总线使用 Kafka。

**理由**：
1. 团队技术栈 Go + Python 混合，REST 调试和运维更简单
2. 内网延迟低（< 1ms），REST 相比 gRPC 的性能差距在本场景可忽略
3. Webhook 天然支持异步解耦，契合 AIGC 长任务场景
4. 减少 Protobuf schema 维护成本

## ADR-005：存储选 MySQL + Redis 而非引入 MongoDB/Elasticsearch

**状态**：已采纳  
**日期**：2026-05-25

### 背景

AIGC 任务元数据 schema 灵活多变，商品搜索需要全文检索能力。

### 方案对比

| 需求 | 原方案 | 当前方案 |
|------|--------|---------|
| 灵活 schema 存储 | MongoDB | MySQL JSON 列 |
| 全文搜索 | Elasticsearch | MySQL FULLTEXT + Redis Search |
| 运维复杂度 | 高（3个数据库系统） | 低（2个系统） |

### 决策

使用 MySQL JSON 列替代 MongoDB，使用 MySQL FULLTEXT 替代 Elasticsearch，保留 Redis 做缓存和搜索加速。

**理由**：
1. MySQL 5.7+ 的 JSON 列支持灵活 schema，满足任务元数据需求
2. 商品数量级在百万级，MySQL FULLTEXT 性能完全满足，无需独立 ES 集群
3. 减少运维复杂度：从 3 套数据库系统降为 2 套（MySQL + Redis）
4. 团队对 MySQL 最熟悉，降低学习和排障成本
